01

Resolved Gaps & Structural Decisions

A. Applicant Resubmission & Audit Trail (FRD §5.2.24 Compliance)

If an applicant is rejected but asked to modify and resubmit, reusing the same Applicant record would overwrite the previous status, timeline, and reviewer comments, violating the audit log integrity requirements.

Technical Resolution

  • Linked-Chain Data Model: Every fresh application submission (including resubmissions) creates a new record in the applicants table.
  • Lineage Tracking: A self-referential foreign key column parent_applicant_id links the new submission to the previous one.
  • Timeline Projection: The admin panel displays a unified "Submission History Timeline" grouping all versions under the same startup concept, keeping comments and scores perfectly isolated and historically queryable.

B. "Accepted" vs. "Confirmed" Status Distinction

Treating "Accepted" and "Confirmed" as a single state creates operational friction. We separate them cleanly in the database and state engine.

State 1: Accepted The startup evaluation panel has approved the startup. An automated email offer is dispatched.
State 2: Confirmed The startup formalizes acceptance by clicking the link, which auto-triggers official email/SSO provisioning.

C. Cohort Status vs. Startup Program Status (The Isolation Principle)

To prevent UI/UX conflation (which FRD explicitly warns against), we strictly decouple these two state engines in separate tables:

Cohort Status (Temporal States)
DRAFT ACTIVE COMPLETED

Describes the cohort as a single collective class.

Startup Program Status (Performance States)
ACTIVE PAUSED GRADUATED KICKED_OUT

Decoupled from global cohort status as required by the FRD.

D. Centralized Governance Center & Granular Permission Nodes

Takhleeq ERP already features a centralized **Governance Center** managing roles and dynamic custom user permissions. To prevent siloed code or permission leaks, we directly **extend** this engine by registering custom, granular permission nodes for all Module 02 features:

Intake & Application Nodes
  • cohort:form_manage: Edit the Dynamic Form Builder, fields schema, and toggle open/close schedules.
  • cohort:applicant_review: Allows screening, grading, adding panel scores, and decision-making.
Cohort Operations Nodes
  • cohort:session_manage: Create, edit, reschedule, or cancel cohort-specific workshop sessions.
  • cohort:attendance_write: Power to mark, edit, and audit daily attendance rosters.
  • cohort:checkin_log: Document structured update feedback, mentors' actions, and progress stages.
  • cohort:warning_write: System power to issue, track, or resolve active performance warnings.
Founder / Delegated Permissions
  • cohort:profile_write: Enables updating self-service parameters (logos, links, bio).
  • cohort:feedback_submit: Grants safe access to submit completely anonymous rating feedback cards.
  • cohort:assignment_upload: Unlocks assignment submission capabilities against deadlined requests.

This guarantees zero permission leaks because administrators can dynamically enable or disable these exact nodes for any staff, manager, or guest role directly from the centralized Governance UI.

02

Updated Lifecycle Flow & Enum Sync

To ensure perfect synchronization with the updated physical flowchart, we have successfully added the following missing statuses to the database enums:

BACKUP_CANDIDATE

Flowchart Sync: Replaces baseline rejected states for qualified backup teams. Creates a formal pool. If space opens, prompts the admin to trigger a custom "Space Opened" invitation email directly.

ORIENTATION_CONDUCTED

Flowchart Sync: Added as a required operational milestone bridge between Confirmation Email Sent and the startup transitioning to Active Cohort. Stores date & orientation log.

Auto-Graduation Business Rule Reconciliation (BR-COH-12)

The Constraint: System auto-graduating active startups upon cohort close clashes with BR-COH-12: "Only authorized staff may modify startup program statuses."

The UX Solution: Instead of silent automated state updates, clicking "Complete Cohort" triggers a confirmation modal: "You are completing Cohort X. Do you want to bulk-graduate the remaining 5 Active startups?" Confirming logs an authorized bulk audit change.

03

Core Operational Modules & Flows

Module A

Admin Dynamic Application Form Builder

Allows administrators to customize intake questionnaires and toggle public availability dynamically with 100% manual accuracy:

  • Always Visible to Admin: The entire dynamic builder, question editor, and configurations are permanently accessible to administrators in the backend.
  • Manual On/Off Toggle Switch: Public submission availability is controlled strictly by a manual toggle switch in the admin panel. If switched **ON**, submissions are accepted; if switched **OFF**, the public portal is locked with a "Submissions Closed" card. No automatic date/time schedules to avoid operational errors.
  • Dynamic Fields Editor: Admin panel lets you add, remove, and sort custom input fields (validated text, numerical entries, CNIC/phone fields, file uploads).
Module B

Public-Facing Applicant Status Lookup Portal

Since applicants do not have login credentials yet, their progress is tracked securely using a zero-friction status lookup system:

  • Secure Tracking Token: Submitting an application automatically triggers an email containing a customized, secure tracking link and Token.
  • State Tracker: Renders a clear linear timeline from Applied up to Decision.
  • Actionable Resubmission Box: If flagged with review issues, the page turns into a clean form displaying staff review comments with an upload field for fast file/details resubmissions.
Module C

Startup Identity & Microsoft SSO Authentication Flow

Keeps system access simple and compliant with Takhleeq corporate accounts:

  • SSO Provisioning: Once an applicant transitions to Confirmed, Takhleeq admins provision standard Microsoft accounts (e.g., startupname@takhleeq.com).
  • Role-Based Router: All login routes lead through a single portal. If a normal student/faculty user logs in, they only see room booking. If an active startup logs in, their sidebar unlocks Module 02.
